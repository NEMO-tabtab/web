# PR

원칙 번호는 [principles.md](principles.md), 제목 형식은 [CONTRIBUTING.md](../CONTRIBUTING.md)의 C4, 승인 인원은 C2를 따릅니다.

## 설명 쓰기

`.github/PULL_REQUEST_TEMPLATE.md`의 세 칸을 채웁니다.

- **Work Description**: 사용자나 코드에 무엇이 달라졌는지. 화면이 바뀌면 스크린샷을 붙입니다.
- **Share**: 리뷰어가 먼저 볼 곳, 고민한 점, 직접 확인한 것.
- **Related issue**: 이 PR로 내용이 모두 해결되는 이슈는 전부 `Closes #번호`, 일부만 해결되면 `Refs #번호`([issues.md](issues.md)의 I3).

## 규칙

**PR1. PR 하나에는 기능 하나만 담는다**
- 규칙: 한 PR은 이슈 하나(작은 기능 하나)만 다루고, 변경이 파일 20개나 500줄을 넘으면 먼저 나눌 수 있는지 본다. 나눌 수 없으면 Share 맨 위에 "먼저 볼 곳"을 적는다.
- 이유: P6, P3. 작아야 되돌리기 쉽고, 리뷰 없이 머지해도 안전하다.
- 강도: 권장 / 확인: 리뷰·자율
- 전제: 일반 PR은 리뷰 없이 머지한다(C2). 리뷰가 없을수록 작아야 한다.
- 예시: #81(파일 2개, 25줄), #93(파일 1개)은 좋은 크기다. #90(파일 80개), #94(파일 31개, 기능 6가지)는 나눌 수 있었다.

**PR2. 미리보기 빌드가 성공한 PR만 머지한다**
- 규칙: PR의 Vercel 상태가 성공이 아니면 머지하지 않는다.
- 이유: P3. 이 빌드가 린트와 타입 검사를 함께 돌린다.
- 강도: 필수 / 확인: 자동(Vercel 상태 표시. 머지를 막는 필수 검사 지정은 후속 이슈)

**PR3. 위험 영역 PR에는 확인한 것과 되돌리는 방법을 적는다**
- 규칙: [위험 영역](production.md#위험-영역) PR은 Share에 ① 직접 확인한 것(실행한 테스트, 눌러 본 화면) ② 문제가 생기면 되돌리는 방법 ③ 이미 저장된 사용자 데이터에 미치는 영향을 적는다.
- 이유: P1, P2, P3.
- 강도: 필수 / 확인: 리뷰(승인하는 사람이 세 가지가 있는지 본다)
- 예시: #94의 설명은 "머지하면 운영 사이트 동작이 바뀝니다"와 확인한 것을 적었다. 되돌리는 방법은 빠져 있다.

**PR4. 리베이스로 머지한다**
- 규칙: 머지는 "Rebase and merge"로 한다. 브랜치를 최신 `main`에 맞출 때는 `main`을 브랜치에 merge하지 않고 `git rebase origin/main`으로 다시 쌓는다. 머지 전에 커밋 제목이 모두 C4 형식인지 확인하고, 자잘한 수정 커밋은 하나로 합친다.
- 이유: P6. 브랜치의 커밋이 그대로 `main`의 기록이 된다. 브랜치에 머지 커밋이 있으면 GitHub이 rebase 머지를 막는다.
- 강도: 필수 / 확인: 자동(`main` 보호 규칙이 rebase 머지만 허용한다)
- 예시: #94는 브랜치에 `main`을 merge한 커밋이 있어 머지가 막혔고, `main` 위로 다시 쌓아 강제 푸시한 뒤에 머지했다.

## 리뷰어가 보는 것

위험 영역 PR에서만 리뷰가 필수입니다. 승인 전에 아래만 확인합니다.

1. PR3의 세 가지가 적혀 있는가
2. [production.md](production.md)의 필수 규칙(R1~R6)을 어기지 않는가
3. 저장소 계층을 고쳤다면 테스트가 함께 바뀌었는가([code-conventions.md](code-conventions.md)의 K3)

코드 모양에 대한 의견은 남겨도 되지만 승인을 막는 이유로 쓰지 않습니다.
