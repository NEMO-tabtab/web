# 원칙

규칙은 모두 여기 원칙 중 하나에서 나옵니다. 규칙이 이상해 보이면 연결된 원칙을 먼저 보고, 원칙에 맞지 않으면 규칙을 고칩니다.

## 원칙과 우선순위

부딪치면 번호가 작은 쪽이 이깁니다.

| # | 원칙 | 이것 때문에 포기하는 것 |
|---|---|---|
| P1 | **기록한 물건은 사라지지 않는다.** 저장 구조·삭제·동기화를 건드리는 변경은 테스트와 다른 한 사람의 확인 없이는 나가지 않는다. | 저장소 쪽 변경의 속도 |
| P2 | **개인정보는 안전한 길로만, 필요한 만큼만.** HTTPS와 본인 확인이 없는 경로로 보내지 않고 로그에 남기지 않는다. | 회원 기능의 일정 |
| P3 | **`main`은 운영이다.** 누구든 PR과 빌드 성공을 거치고, 되돌리는 방법을 모르는 변경은 머지하지 않는다. | 급할 때의 직접 push |
| P4 | **기기가 먼저, 서버는 뒤에서 아껴 쓴다.** 등록·조회·수정은 인터넷 없이 되고, 로그인한 사용자의 데이터만 서버에 바뀐 만큼만 보낸다. | 서버에서 바로 읽어 오는 손쉬운 구현 |
| P5 | **화면은 공통 부품과 토큰으로만 만든다.** 새 모양이 필요하면 부품을 먼저 고친다. | 화면 하나만 빨리 꾸미는 자유 |
| P6 | **규칙은 도구가 지키게 하고, 사람이 기억할 규칙은 적게 둔다.** 작은 PR로 자주 합친다. | 세세한 스타일 규칙, 한 번에 크게 합치는 편함 |

예: 오프라인 동작(P4)을 위해 개인정보를 기기에 그대로 쌓아야 한다면 P2가 이깁니다. 디자인 완성도(P5) 때문에 저장 버그 수정이 늦어진다면 P1이 이깁니다.

## 엄격함을 두는 곳

"필수" 규칙은 아래 **위험 영역**과, 작업 흐름의 뼈대 세 가지(이슈에서 시작, `main`에는 PR로만, 해결된 이슈 닫기)에만 둡니다. 나머지는 "권장"이고 리뷰 없이 본인이 머지합니다.
위험 영역의 정의는 [production.md](production.md#위험-영역) 한 곳에 있습니다.

## 지금은 신경 쓰지 않는 것

(추정 — 팀 확인 필요) 다크 모드, 다국어, 데스크톱 전용 화면, 성능 수치 목표, 화면 테스트 자동화.

## 규칙을 바꾸는 방법

- 원칙(이 파일): 팀 세 명의 합의 후 PR.
- 규칙(나머지 문서): 이유를 적은 PR. 위험 영역 규칙이면 다른 1명 승인.
- 규칙을 새로 넣을 때는 어느 원칙에서 나왔는지 적습니다. 못 적으면 넣지 않습니다.
- 주요 결정은 [decisions/](decisions/)에 한 장으로 남깁니다.

## 다시 점검할 때

- 팀원이 들어오거나 나갈 때 (리뷰 인원 규칙의 전제)
- 일반 공개 출시 전후
- 서버 동기화를 시작할 때, 새로운 종류의 사용자 데이터를 다루게 될 때
- 같은 규칙이 세 번 이상 어겨졌을 때 (자동화하거나 없앨 후보)
