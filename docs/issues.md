# 이슈

원칙 번호는 [principles.md](principles.md), 제목 형식은 [CONTRIBUTING.md](../CONTRIBUTING.md)의 C4를 따릅니다.

## 종류와 템플릿

| 종류 | 제목 | 템플릿 |
|---|---|---|
| 기능·개선·정리 | `[feat]`, `[refactor]`, `[style]`, `[docs]`, `[chore]` | `.github/ISSUE_TEMPLATE/feature-request.md` (기존) |
| 버그 | `[fix]` | `.github/ISSUE_TEMPLATE/bug-report.md` |

## 라벨

GitHub 기본 라벨 중 아래만 씁니다. 종류는 제목에 이미 있으므로 라벨로 다시 붙이지 않습니다.

| 라벨 | 뜻 |
|---|---|
| `bug` | 사용자가 겪는 오동작 |
| `risk` (새로 만들 라벨) | [위험 영역](production.md#위험-영역)을 건드림 — PR에 승인 1명이 필요하다는 표시 |
| `urgent` (새로 만들 라벨) | 아래 "긴급"에 해당 |

## 우선순위

두 단계만 둡니다.

- **긴급(`urgent`)**: 사용자의 기록이 사라지거나, 개인정보가 노출되거나, 앱을 쓸 수 없는 상태. 하던 일을 멈추고 먼저 합니다 → [production.md](production.md#긴급-수정)
- **보통**: 그 밖의 전부. 라벨 없음.

## 규칙

**I1. 이슈 하나는 PR 하나로 끝낼 크기로 쓴다**
- 규칙: 한 PR로 끝내기 어려운 일은 작은 이슈 여러 개로 나누고, 묶음 이슈에는 체크리스트로 하위 이슈를 건다.
- 이유: P6. 작은 PR의 출발점이다.
- 강도: 권장 / 확인: 자율
- 예시: #79(디자인 시스템 재구축)는 브랜치 4개와 파일 80개짜리 PR로 이어졌다. `[feat] 숫자 입력에 쉼표 표시`처럼 나눴다면 각각 따로 합칠 수 있었다(#86은 요청 여러 개가 한 이슈에 들어 있다).

**I2. 시작해도 되는 이슈에는 완료 조건이 있다**
- 규칙: 작업을 시작하기 전에 이슈에 "무엇이 되면 끝인지"가 한 줄 이상 적혀 있고 담당자가 지정돼 있어야 한다.
- 이유: P6.
- 강도: 권장 / 확인: 자율
- 예시: #88은 "로그인시 정보 저장"뿐이라 무엇을 어디에 저장하면 끝인지 알 수 없다.

**I3. 끝난 이슈는 PR이 닫는다**
- 규칙: PR 설명의 Related issue에 `Closes #번호`를 적어 머지와 함께 닫히게 한다.
- 이유: P6.
- 강도: 권장 / 확인: 자동(PR 템플릿)
- 예시: #67은 PR #68이 머지됐는데도 열려 있다.
