# 운영과 사용자 데이터

실제 사용자에게 피해가 가고 되돌리기 어려운 영역의 규칙입니다. 이 문서의 규칙은 대부분 **필수**입니다.
규칙 형식: 규칙 / 이유(원칙 번호는 [principles.md](principles.md)) / 강도 / 확인 방법 / 전제 / 예시.

## 위험 영역

아래를 건드리는 PR이 "위험 영역 PR"입니다. 다른 문서는 이 목록을 링크로만 가리킵니다.

| 영역 | 경로 | 잘못되면 |
|---|---|---|
| 기기 저장소 | `src/lib/db/` (PR #94에서 추가) | 사용자의 기록이 사라지고 복구할 수 없음 |
| 서버 통신·동기화 | 서버를 부르는 코드 전부, 앞으로 생길 동기화 계층 | 기록 유실·중복, 서버 비용 |
| 개인정보·인증 | `src/app/login/`, `src/app/signup/`, `src/app/(user)/` | 주소·이메일 노출, 남의 계정 접근 |
| 캐시·배포 설정 | `src/app/sw.ts`(PR #94), `next.config.mjs`, 환경변수 | 낡은 화면이 기기에 남거나 빌드가 깨짐 |

## 규칙

**R1. 저장 구조는 새 버전을 추가해서만 바꾼다**
- 규칙: `src/lib/db/index.ts`의 이미 배포된 `this.version(n).stores(...)`는 고치지 않고, 새 `version(n+1)`과 업그레이드 테스트를 함께 추가한다.
- 이유: P1. 사용자 기기의 데이터는 우리가 되돌릴 수 없다. Vercel 롤백도 기기 안 데이터는 되돌리지 못한다.
- 강도: 필수 / 확인: 리뷰(다른 1명) + `pnpm test`
- 예시: 지금은 `version(1)` 하나뿐이다. 필드에 색인을 더하려면 `version(2)`를 추가한다.

**R2. 물건 삭제는 표시만 한다**
- 규칙: 물건 기록은 지우지 않고 `deletedAt`만 채운다. 여러 건을 한꺼번에 지우거나 저장소를 비우는 코드는 위험 영역 PR로 다룬다.
- 이유: P1, P4. 서버에 삭제를 알리려면 기록이 남아 있어야 한다.
- 강도: 필수 / 확인: 리뷰 + 테스트
- 예시: `src/lib/db/products.ts`의 `deleteProduct` (사진은 용량 때문에 바로 지운다).

**R3. 개인정보는 HTTPS와 로그인된 본인의 요청으로만 주고받는다**
- 규칙: `http://` 주소, 코드에 직접 적은 서버 주소, 고정된 사용자 번호로 개인정보를 보내거나 받는 코드를 머지하지 않는다.
- 이유: P2.
- 강도: 필수 / 확인: 리뷰(다른 1명)
- 예시(지금 어기고 있는 곳): `src/app/(user)/user-edit/page.tsx`가 `http://3.38.247.4:8080/api/user/1`을 부른다. 고칠 때까지 이 화면은 막는다(후속 이슈).

**R4. 개인정보를 로그에 남기지 않는다**
- 규칙: 입력값, 서버 응답 본문, 사용자 식별 정보를 `console.*`에 넘기지 않는다.
- 이유: P2. 오류 추적 도구를 붙이면 콘솔 내용이 그대로 밖으로 나간다.
- 강도: 필수 / 확인: 리뷰
- 예시(고칠 곳): `src/app/signup/page.tsx`의 `console.error("회원가입 서버 오류:", errorText)`.

**R5. 비밀값은 저장소와 브라우저에 두지 않는다**
- 규칙: `.env`는 커밋하지 않고, `NEXT_PUBLIC_`으로 시작하는 변수에는 공개돼도 되는 값만 넣는다. 새 변수는 `.env.example`에 이름만 추가한다.
- 이유: P2. 저장소가 공개이고, `NEXT_PUBLIC_` 값은 누구나 볼 수 있다.
- 강도: 필수 / 확인: 자동(`.gitignore`) + 리뷰
- 예시: `.env`가 #82에서 한 번 커밋됐다(키는 `NEXT_PUBLIC_API_URL` 하나). PR #89가 정리 중.

**R6. 기기에 먼저 저장하고, 서버에는 바뀐 것만 보낸다**
- 규칙: 화면의 저장·수정·삭제는 기기 저장이 끝나면 성공이다. 서버 전송은 로그인한 사용자에 한해 뒤에서 하고, 마지막 동기화 이후 바뀐 기록만 묶어서 보낸다. 정해진 간격으로 서버를 계속 부르는 코드(폴링)는 넣지 않는다.
- 이유: P4, P1.
- 강도: 필수 / 확인: 리뷰(다른 1명)
- 전제: 동기화는 아직 구현 전이다. 구체적인 방식은 [decisions/0001-local-first-sync.md](decisions/0001-local-first-sync.md)의 방향을 따르고, 구현하면서 이 규칙을 구체화한다.

## 환경

| 환경 | 어디 | API 주소 |
|---|---|---|
| 운영 | `main` → Vercel Production. Android 앱도 이 사이트를 띄운다 | Vercel 환경변수 |
| 미리보기 | PR마다 Vercel Preview | 없음 — 빌드는 되지만 서버를 부르는 화면은 동작하지 않는다 |
| 로컬 | `pnpm dev` | 각자의 `.env` |

## 배포와 되돌리기

- `main`에 머지하면 바로 운영에 나갑니다. 스토어에 새 버전을 올리지 않아도 Android 앱 안 화면이 바뀝니다.
- 서비스 워커(PR #94)는 새 버전을 받는 즉시 교체합니다(`skipWaiting`). 잘못된 버전도 즉시 퍼집니다.
- 되돌리기: Vercel에서 이전 배포로 롤백하거나 되돌리는 PR을 머지합니다. (Vercel 권한이 누구에게 있는지는 미확인)
- **기기 안 데이터는 되돌릴 수 없습니다.** 그래서 R1·R2가 필수입니다.
- 앱 아이콘·로딩 화면처럼 앱 껍데기에 든 것만 스토어 업로드가 필요합니다. 껍데기 프로젝트와 서명 키는 이 저장소 밖에 있습니다(보관 위치와 공유 여부는 미확인).

## 긴급 수정

1. `fix/설명` 브랜치에서 고치고 PR을 엽니다. 이슈는 머지 전까지 만들어 PR에 연결합니다.
2. 미리보기 빌드가 성공하면 머지합니다. 위험 영역이면 긴급이어도 다른 1명의 승인을 받습니다.
3. 고치는 것보다 되돌리는 것이 빠르면 먼저 롤백합니다.

## 나중에

- 오류 추적 도구 도입, 장애 알림: 일반 공개 전에 결정.
- 백업 내보내기·가져오기(지금은 비활성): 서버 동기화 전까지 P1의 유일한 안전망이므로 우선순위를 높게 봅니다.
- 백엔드 DB 변경 절차: 백엔드 저장소의 몫이라 여기서는 다루지 않습니다.
